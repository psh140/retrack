# AI 에이전트 하네스 설계 기록

작성일: 2026-08-06

Retrack은 개발 전 과정에서 Claude Code를 사용했고, 반복 작업을 자동화하기 위해
**하네스(harness)** 라는 형태로 전문 에이전트와 스킬을 구성해 썼다.
이 문서는 그 구성의 **판단 근거**를 남긴다.

파일 목록 자체는 `.claude/agents/`, `.claude/skills/`를 열면 알 수 있다.
여기 적는 것은 열어봐도 알 수 없는 것 — **왜 그렇게 나눴고, 무엇이 잘 됐고 무엇이 어긋났는지**다.

> **다른 도구로 옮길 때 주의**
> 이 구성은 Claude Code의 스킬·서브에이전트 메커니즘에 맞춰 만든 것이다.
> `.claude/` 아래 파일을 다른 도구로 그대로 복사하는 것은 권하지 않는다.
> 이 문서를 **재료**로 삼아, 해당 도구의 실제 스펙에 맞춰 새로 설계하는 편이 낫다.
> 하네스는 추측이 아니라 반복 작업에서 나온다 — 아래 "개정 이력"이 그 증거다.

---

## 1. 왜 하네스를 썼는가

이 프로젝트는 구현 패턴이 강하게 반복된다. 한 기능을 추가할 때 손대는 파일이 매번 같은 모양이다.

```
Controller → Service → Mapper 인터페이스 → VO → MyBatis XML
```

레이어가 고정되어 있고 각 레이어의 규칙(주석 형식, 예외 처리 방식, 권한 어노테이션)도 고정되어 있다.
매번 같은 지시를 반복하는 대신 규칙을 문서로 고정하고 역할을 나눈 것이 하네스의 출발점이다.

---

## 2. 개정 이력 — 세 번 고쳤다

| 날짜 | 변경 | 사유 |
|---|---|---|
| 2026-05-10 | 초기 구성 (백엔드 4개) | 반복 구현 패턴 자동화 |
| 2026-05-10 | 프론트엔드 팀 추가 (3개) | 페이지 단위 React 구현 자동화 |
| 2026-05-18 | 프론트엔드 QA 강화 | 백엔드보다 사용자 수동 검토 비중이 높아 자동화 필요 |

**세 번째 개정이 핵심이다.** "프론트엔드는 백엔드보다 결과물을 사람이 직접 눈으로 확인해야 하는
비중이 높다"는 것은 미리 알 수 있는 사실이 아니었다. 백엔드 하네스를 그대로 프론트엔드에 복사해
써 본 뒤에야 드러났다. 처음부터 완성된 하네스를 설계하려 하지 말 것.

## 3. 구성

### 에이전트 7개

| 에이전트 | 역할 |
|---|---|
| `backend-leader` | 백엔드 오케스트레이터. 요청을 레이어별로 분해·분배하고 검증을 조율 |
| `java-implementer` | Controller / Service / Mapper 인터페이스 / VO 구현 |
| `mybatis-specialist` | `resources/mapper/` 의 MyBatis XML 전담 |
| `quality-guardian` | 규칙 준수 검증 + **직접 수정** |
| `frontend-leader` | 프론트엔드 오케스트레이터 |
| `ui-builder` | React 페이지·공통 컴포넌트 구현 |
| `api-connector` | axios 인스턴스, JWT 인터셉터, API 호출 함수 |

### 스킬 8개

| 스킬 | 용도 |
|---|---|
| `retrack-backend` | 백엔드 단계별 구현 오케스트레이션 (진입점) |
| `retrack-frontend` | 프론트엔드 페이지/컴포넌트 구현 오케스트레이션 (진입점) |
| `java-layer` | Java 레이어 작성 패턴 |
| `mybatis-query` | MyBatis XML 작성 패턴 (PostgreSQL 문법) |
| `react-page` | React 페이지 컴포넌트 패턴 |
| `api-integration` | axios 연동 패턴 |
| `code-quality-check` | 품질 검증 절차 |
| `retrack-design` | 색상·타이포·로고·아이콘·UI 키트 — 시각적 결정 전담 |

**에이전트와 스킬을 나눈 이유**: 에이전트는 *누가 하는가*(역할과 조율 규칙),
스킬은 *어떻게 쓰는가*(구현 패턴과 코드 템플릿)를 담는다.
스킬은 에이전트 없이 단독 호출도 가능해서, 작은 작업에는 오케스트레이터를 거치지 않고 바로 쓸 수 있었다.

## 4. 분리 판단의 근거

### `java-implementer`와 `mybatis-specialist`를 왜 나눴는가

Java 레이어와 MyBatis XML은 **서로 다른 실수를 한다.**

- Java 쪽 빈발 실수: Javadoc 누락, `@RequiredRole` 누락, Controller에 try-catch를 넣는 것
- XML 쪽 빈발 실수: `resultType`만 쓰고 `<resultMap>`을 생략하는 것

특히 두 번째가 위험하다. snake_case 컬럼과 camelCase 필드가 어긋나면 **에러 없이 필드가 조용히
`null`로 반환된다.** 컴파일도 통과하고 쿼리도 성공하는데 값만 비어 있다.
이 실패 모드를 아는 전담 역할을 두는 편이 한 에이전트에게 둘 다 시키는 것보다 나았다.

부수 효과로 두 레이어를 병렬로 구현할 수 있었다.

### `quality-guardian`을 왜 별도로 뒀는가

**주석 누락이 이 프로젝트에서 가장 자주 발생한 규칙 위반이었다.**
구현하는 쪽에게 "구현하면서 주석도 챙겨라"라고 시키면 기능이 우선순위를 가져가서 주석이 밀린다.
구현과 검증을 분리하고, 검증자에게 두 가지 제약을 걸었다.

1. **보고만 하지 말고 직접 고친다** — 지적만 하면 사람이 다시 지시해야 해서 왕복이 늘어난다
2. **기능은 건드리지 않는다** — 주석·네이밍·규칙만 교정한다. 검증자가 로직을 바꾸면 검증이 아니라 재구현이 된다

### `retrack-design`을 왜 따로 뒀는가

초기 UI 결과물의 품질에 불만이 있었다. 원인은 시각적 결정(색상·간격·컴포넌트 스타일)을
매번 즉흥적으로 내린 것이었다. 디자인 토큰과 에셋을 스킬로 고정하고
**"임의 디자인 금지"** 를 규칙으로 못박은 뒤 일관성이 잡혔다.
2026-07-24 UI 일관성 개선 5단계 작업이 이 스킬을 기반으로 진행됐다.

## 5. 실제로 어긋난 부분 — 재구성 전에 볼 것

하네스 정의 파일은 **작성 시점(2026-05)에 멈춰 있고 이후 코드 변경을 따라가지 못했다.**
그대로 믿고 재사용하면 안 된다. 확인된 불일치는 다음과 같다.

| 위치 | 정의된 내용 | 실제 |
|---|---|---|
| `api-connector` | `baseURL: 'http://localhost:8080'` | `baseURL: '/api'` — nginx 리버스 프록시로 전환됨 |
| `ui-builder` | 페이지 파일이 `.js` | 전부 `.jsx` |
| `ui-builder` / `frontend-leader` | `BudgetPage`, `FilePage` 존재 | 없음. 연구비·파일 기능은 `ProjectDetailPage`에 통합 |
| `frontend-leader` | 페이지 목록 11개 | `LandingPage`, `ActivityLogPage` 누락 (이후 추가된 페이지) |
| 루트 `CLAUDE.md` 변경 이력 | 2026-05-18 `frontend-qa` 추가 | **해당 에이전트 파일이 없다.** 계획만 기록되고 실제로 만들어지지 않았거나 이후 삭제됨 |

**여기서 얻을 교훈**: 하네스 정의는 코드가 아니라 문서라서 CI가 잡아주지 않는다.
정의에 구체적인 값(파일명, URL, 목록)을 하드코딩할수록 빨리 낡는다.
재구성한다면 **변하지 않는 것(규칙·원칙·실패 모드)만 정의에 넣고,
변하는 것(파일 목록·엔드포인트)은 코드를 직접 읽게 하는 편**이 낫다.

## 6. 잘 된 것 / 아쉬운 것

**잘 된 것**

- 레이어 분리 구현 — 반복 패턴이 강한 프로젝트에서 효과가 컸다
- 검증 역할 분리 — 주석 규칙이 12단계 내내 유지됐다
- 디자인 시스템 고정 — 임의 결정을 막으니 일관성이 확보됐다

**아쉬운 것**

- 정의 파일의 노후화를 관리할 방법이 없었다 (5장)
- 프론트엔드 QA 자동화는 계획만 남고 완결되지 않았다
- 에이전트 정의와 스킬 내용이 일부 중복된다. 규칙을 고칠 때 양쪽을 다 봐야 했다
