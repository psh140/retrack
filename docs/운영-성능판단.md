# 운영·성능 판단

> 대상: `docker-compose.prod.yml`, `frontend/nginx.prod.conf`, `ProjectService`, `ProjectMapper.xml`, `spring-db.xml`

운영 환경에서 자원을 어디까지 쓰게 둘지 정한 판단들을 모았다.
대부분 개발 단계에서 미리 넣은 것이고, 첫 항목만 실제 운영 관찰에서 나왔다.

---

## 1. 컨테이너 로그 로테이션 — 운영에서 발견한 것

Docker의 기본 `json-file` 로깅 드라이버는 **로그 크기에 상한이 없다.**
컨테이너가 죽지 않는 한 로그 파일은 계속 커진다.

배포 후 로그 증가량을 확인해 보니 **하루 약 100MB** 수준이었다. 두 가지가 겹친 결과다.

- 백엔드가 MyBatis SQL을 DEBUG 레벨로 남긴다 (`log4j2.xml`의 `com.retrack.mapper`가 DEBUG).
- 공개 IP에 붙은 뒤로 봇 스캔 트래픽이 끊이지 않고 들어온다.

EC2 인스턴스의 디스크는 20GB다. 하루 100MB는 단순 계산으로 200일이면 전부를 채우는 양이다.
디스크가 차면 DB 쓰기부터 실패하므로 서비스 전체가 멈춘다.

서비스당 `max-size: 10m` × `max-file: 3`으로 상한을 걸었다.
서비스당 최대 30MB, 세 서비스를 합쳐 90MB에서 더 늘지 않는다.

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

`x-` 접두사가 붙은 최상위 필드는 Compose가 서비스로 해석하지 않는 확장 영역이다.
YAML 앵커(`&default-logging`)로 정의해 두고 db·backend·frontend 세 서비스가
`logging: *default-logging`으로 같은 설정을 참조한다.
세 곳에 같은 블록을 복사하면 한 곳만 고치고 지나치기 쉬워 앵커로 묶었다.

로그 보존 기간이 짧아지는 것은 감수한 부분이다.
장애를 늦게 발견하면 원인 구간의 로그가 이미 밀려나 있을 수 있다.
로그 수집 체계를 갖추기 전까지의 절충이다.

## 2. 페이지 크기 화이트리스트

목록 조회의 `size` 파라미터는 **10, 20, 50만 받는다.**

```java
private static final List<Integer> VALID_PAGE_SIZES = Arrays.asList(10, 20, 50);

if (!VALID_PAGE_SIZES.contains(size)) {
    throw new BadRequestException("페이지 크기는 10, 20, 50만 허용됩니다.");
}
```

`size`는 그대로 SQL의 `LIMIT`으로 내려간다.
상한을 두지 않으면 `?size=1000000` 한 번으로 테이블 전체를 읽어 직렬화까지 하게 된다.
프론트엔드가 10/20/50만 보내더라도 API는 직접 호출될 수 있으므로 서버에서 막는다.

`page`는 별도로 `page < 1`을 막는다. 음수가 들어오면 `(page - 1) * size`가 음수 OFFSET이 되어
PostgreSQL이 오류를 반환한다.

## 3. 페이지네이션 쿼리 구조

페이지네이션은 목록 조회(`findAll`)와 총 건수 조회(`countAll`) 두 번의 쿼리로 이뤄진다.
두 쿼리의 WHERE 절이 어긋나면 **목록에는 안 나오는 건수**가 표시된다.
검색 조건이 여덟 개라 양쪽을 따로 관리하면 조건 하나를 추가할 때마다 어긋날 여지가 생긴다.

조건을 `<sql>` 프래그먼트 하나로 빼고 양쪽에서 `<include>`한다.

```xml
<sql id="projectSearchConditions">
    <where>
        <if test="keyword != null and keyword != ''">
            title ILIKE '%' || #{keyword} || '%'
        </if>
        <if test="status != null and status != ''">
            AND status = #{status}
        </if>
        <!-- userId, managerId, startDateFrom/To, endDateFrom/To ... -->
    </where>
</sql>
```

```xml
<select id="findAll" ...>
    SELECT ... FROM projects
    <include refid="projectSearchConditions"/>
    ORDER BY created_at DESC
    LIMIT #{size} OFFSET #{offset}
</select>

<select id="countAll" ...>
    SELECT COUNT(*) FROM projects
    <include refid="projectSearchConditions"/>
</select>
```

조건이 늘어나도 고칠 곳은 한 군데다.

정렬은 `created_at DESC` 고정이고, 여기에 맞춰
`idx_projects_created_at ON projects(created_at DESC)` 인덱스를 정렬 방향까지 같게 만들어 두었다.

## 4. 검색 성능의 한계와 개선 경로

과제명 검색은 `ILIKE '%keyword%'`다. 앞뒤 양쪽에 와일드카드가 붙는다.

```
title ILIKE '%' || #{keyword} || '%'
```

B-tree 인덱스는 값의 **앞에서부터** 정렬되어 있어 앞이 고정된 패턴만 탐색 구간을 좁힐 수 있다.
`'검색어%'`는 인덱스를 타지만 `'%검색어%'`는 시작 위치를 알 수 없어 전체 행을 훑는다.
`title`에 인덱스를 추가해도 이 쿼리는 여전히 full scan이다.

지금은 그대로 두었다. 과제 수가 적어 full scan의 비용이 문제 되는 규모가 아니고,
아래 개선안은 모두 확장 설치나 인덱스 추가를 동반해 운영 부담이 생긴다.

필요해질 때의 경로는 `pg_bigm` 확장 + GIN 인덱스다.
`pg_trgm`이 아니라 `pg_bigm`인 이유는 한국어 때문이다.
`pg_trgm`은 3글자 단위(trigram)로 쪼개므로 두 글자 검색어가 인덱스를 활용하지 못하는데,
한국어에서는 "예산", "승인" 같은 두 글자 검색이 흔하다.
`pg_bigm`은 2글자 단위라 이 경우를 받아낸다.

전환 시점의 판단 기준은 과제 수보다 **목록 조회의 응답 시간**이 될 것이다.
현재는 측정 근거가 없어 임계값을 정해두지 않았다.

## 5. 정적 자산 캐시 전략

Vite는 빌드 시 파일명에 콘텐츠 해시를 붙인다(`index-a1b2c3d4.js`).
내용이 바뀌면 파일명이 바뀌므로, 같은 이름의 파일은 영원히 같은 내용이다.
캐시 무효화를 걱정할 이유가 없어 `immutable`로 1년 캐시를 건다.

```nginx
location ~* \.(js|css|svg|woff2?|ico|png|jpg)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
    ...
}
```

`index.html`은 이 패턴에 걸리지 않는다. 확장자가 `.html`이라 목록에 없다.
해시가 붙지 않는 유일한 진입점이므로 항상 새로 받아야 하고,
새 `index.html`이 새 해시 파일명을 참조하면서 배포분이 반영된다.

정규식 `location`은 prefix `location`(`/`)보다 우선순위가 높다.
그럼에도 SPA 폴백과 충돌하지 않는 것은 정규식이 **확장자로 끝나는 요청만** 잡기 때문이다.
`/dashboard`, `/projects/12` 같은 라우트 경로에는 확장자가 없어 `location /`의
`try_files $uri /index.html`로 넘어간다.

보안 헤더는 정적 자산 블록에서 다시 선언한다.
nginx의 `add_header`는 **하위 블록에 `add_header`가 하나라도 있으면 상위 블록의 것을 상속하지 않는다.**
`Cache-Control` 하나를 추가한 탓에 서버 블록의 보안 헤더 네 종이 통째로 빠지므로,
같은 블록 안에 다시 적어 둔다.

## 6. HikariCP 커넥션 풀 설정

`spring-db.xml`의 현재 설정값이다.

| 항목 | 값 |
|---|---|
| `maximumPoolSize` | 10 |
| `minimumIdle` | 2 |
| `connectionTimeout` | 30,000ms (30초) |
| `idleTimeout` | 600,000ms (10분) |
| `maxLifetime` | 1,800,000ms (30분) |

`DriverManagerDataSource`에서 `HikariDataSource`로 교체하면서 함께 넣었고,
`destroy-method="close"`를 지정해 Tomcat 종료 시 커넥션이 반납되도록 했다.

이 수치들은 부하 측정에 근거해 정한 값이 아니다.
동시 접속 규모를 측정한 뒤에 조정할 대상으로 남겨 둔다.
