# 설계 판단 — 데이터 모델

> 대상: `sql/schema.sql`, `ProjectService`, `FileService`

테이블 사이의 삭제 정책, 상태 전이 규칙, 인덱스 구성을 정한 기록이다.

---

## 1. FK 삭제 정책을 두 갈래로 나눈 기준

모든 외래키에 `ON DELETE` 동작을 명시했고, 기준은 **소유냐 참조냐**다.

**소유 관계 → `ON DELETE CASCADE`**

부모가 사라지면 자식의 존재 이유도 사라지는 관계다.

```sql
-- PROJECT_HISTORY / BUDGET / FILES
project_id  BIGINT NOT NULL REFERENCES PROJECTS(project_id) ON DELETE CASCADE,
```

과제가 지워지면 그 과제의 상태 이력·연구비 내역·첨부파일 레코드는 남을 이유가 없다.
과제 없이 존재하는 연구비 집행 내역은 어디에도 붙지 못한 데이터다.

**참조 관계 → `ON DELETE SET NULL`**

"누가 했는가"를 가리키는 컬럼이다.

```sql
changed_by  BIGINT REFERENCES USERS(user_id) ON DELETE SET NULL,  -- PROJECT_HISTORY
used_by     BIGINT REFERENCES USERS(user_id) ON DELETE SET NULL,  -- BUDGET
uploaded_by BIGINT REFERENCES USERS(user_id) ON DELETE SET NULL,  -- FILES
manager_id  BIGINT REFERENCES USERS(user_id) ON DELETE SET NULL,  -- PROJECTS
```

여기를 CASCADE로 두면 **사용자 한 명을 지울 때 그 사람이 남긴 기록이 함께 사라진다.**
연구비를 집행한 담당자가 퇴사하면 집행 내역이 통째로 없어지고, 과제의 예산 합계가
설명 없이 줄어든다. 상태 변경 이력도 마찬가지로 중간이 비어버린다.

연구과제 관리에서 이력은 "지금 상태"만큼 중요하다.
언제 누가 승인했고 반려 사유가 무엇이었는지가 남아 있어야 감사에 대응할 수 있다.
행위자가 조직을 떠나는 것과 그 행위가 있었다는 사실은 별개이므로,
사람은 지워지되 기록은 남고 행위자 자리만 비도록 `SET NULL`로 정했다.

이 결정에 따라 해당 컬럼들의 `NOT NULL` 제약도 함께 제거했다.
`SET NULL`은 컬럼이 `NULL`을 허용해야 동작한다.

한편 `ACTIVITY_LOGS.user_id`와 `NOTIFICATIONS.user_id`는 `CASCADE`다.
활동 로그와 알림은 특정 사용자에게 귀속된 데이터라 사용자가 사라지면
수신자도 조회 주체도 없어진다. 반면 `NOTIFICATIONS.project_id`는 `SET NULL`이라
과제가 지워져도 발송된 알림 기록 자체는 남는다.

## 2. 스키마 정책이 애플리케이션 코드로 이어진 지점

`SET NULL`은 "그 컬럼이 언젠가 `NULL`이 된다"는 뜻이므로 코드가 그 상태를 해석해야 한다.

파일 삭제 권한 검사가 그 지점이다.

```java
// uploadedBy가 null이면 업로더가 탈퇴한 경우 — ADMIN만 삭제 가능
if (!"ADMIN".equals(requesterRole) &&
        (file.getUploadedBy() == null || !file.getUploadedBy().equals(requesterUserId))) {
    throw new UnauthorizedException("본인이 업로드한 파일만 삭제할 수 있습니다.");
}
```

RESEARCHER는 본인이 올린 파일만 지울 수 있는데, `uploadedBy`가 `NULL`이면
비교 대상이 없다. 이 파일은 **주인이 없는 상태**다.

`NULL` 체크를 빼면 `file.getUploadedBy().equals(...)`에서 NPE가 나고,
반대로 `NULL`을 "누구나 지워도 되는 파일"로 해석하면 탈퇴한 사용자의 자료가
아무에게나 열린다. 그래서 ADMIN에게만 넘긴다.

스키마의 삭제 정책 하나가 서비스 레이어의 분기를 만든 사례다.

## 3. 상태 전이 규칙을 코드로 강제

과제 상태는 임의로 바뀌지 않는다. 허용된 다음 상태를 맵으로 고정했다.

```java
private static final Map<String, List<String>> VALID_TRANSITIONS = new HashMap<>();
static {
    VALID_TRANSITIONS.put("DRAFT",       Arrays.asList("SUBMITTED"));
    VALID_TRANSITIONS.put("SUBMITTED",   Arrays.asList("REVIEWING"));
    VALID_TRANSITIONS.put("REVIEWING",   Arrays.asList("APPROVED", "REJECTED"));
    VALID_TRANSITIONS.put("APPROVED",    Arrays.asList("IN_PROGRESS"));
    VALID_TRANSITIONS.put("IN_PROGRESS", Arrays.asList("COMPLETED"));
    VALID_TRANSITIONS.put("REJECTED",    Arrays.asList());
    VALID_TRANSITIONS.put("COMPLETED",   Arrays.asList());
}
```

전이도로 보면 다음과 같다.

```
  DRAFT ──▶ SUBMITTED ──▶ REVIEWING ─┬──▶ APPROVED ──▶ IN_PROGRESS ──▶ COMPLETED ●
                                     │
                                     └──▶ REJECTED ●

  ● = 종료 상태 (허용된 다음 상태 없음)
```

`REJECTED`와 `COMPLETED`는 빈 리스트를 값으로 갖는다.
키를 아예 두지 않아도 `null` 체크에 걸려 같은 결과가 나오지만, 빈 리스트를 명시했다.
"다음 상태가 없는 종료 상태"와 "규칙을 등록하지 않은 상태"는 다른 뜻이고,
새 상태를 추가할 때 이 맵만 보면 전체 흐름을 알 수 있다.

검사는 상태값 자체의 유효성과 전이 가능 여부 두 단계다.

```java
if (!VALID_STATUSES.contains(newStatus)) {
    throw new BadRequestException("유효하지 않은 상태값입니다.");
}
```

값 검증을 먼저 하는 이유는 오류 메시지 때문이다.
`ABCD` 같은 존재하지 않는 값이 들어왔을 때 "전이가 허용되지 않습니다"라고 답하면
호출자가 원인을 잘못 짚는다.

## 4. MANAGER 이상의 규칙 우회

전이 규칙은 RESEARCHER 이하에만 적용된다.

```java
// MANAGER 이상은 전이 규칙 없이 모든 상태로 변경 가능
boolean isManagerOrAbove = "MANAGER".equals(userRole) || "ADMIN".equals(userRole);
if (!isManagerOrAbove) {
    List<String> allowedNext = VALID_TRANSITIONS.get(project.getStatus());
    if (allowedNext == null || !allowedNext.contains(newStatus)) {
        throw new BadRequestException(
                project.getStatus() + " → " + newStatus + " 전이는 허용되지 않습니다."
        );
    }
}
```

의도적으로 열어둔 구멍이다.

전이도는 정상 흐름을 그린 것이고, 실무에서는 그 흐름을 벗어나는 일이 생긴다.
승인 처리한 과제에 오류가 발견되어 검토 단계로 되돌려야 하거나,
반려된 과제를 재검토하기로 결정하는 경우다.
규칙을 예외 없이 강제하면 이런 상황에서 DB를 직접 수정하게 되고,
그 순간 상태 변경 이력과 알림이 남지 않는다.

관리자에게 되돌릴 권한을 주되 **경로는 그대로 API를 타게** 하는 편이 낫다고 봤다.
MANAGER가 되돌린 것도 `PROJECT_HISTORY`에 이력으로 남고,
`ActivityLogAspect`가 `PROJECT_STATUS_CHANGE` 로그를 기록하며, 알림도 나간다.
규칙을 우회해도 흔적은 남는다.

값 자체의 유효성 검사(`VALID_STATUSES`)는 권한과 무관하게 항상 적용된다.
관리자라도 정의되지 않은 상태값은 넣을 수 없다.

## 5. 인덱스 설계

11개를 `IF NOT EXISTS`로 선언했다. 선정 기준은 실제 쿼리의 접근 경로다.

**목록 조회의 정렬**

```sql
CREATE INDEX IF NOT EXISTS idx_projects_created_at ON projects(created_at DESC);
```

과제 목록은 `ORDER BY created_at DESC`로 고정이다.
인덱스의 정렬 방향을 쿼리와 같게 맞추면 정렬 연산 없이 인덱스를 앞에서부터 읽는다.
방향이 반대여도 PostgreSQL은 역방향 스캔이 가능하지만,
쿼리와 같은 방향으로 두는 편이 실행 계획이 단순해진다.

**검색 조건 컬럼**

`idx_projects_status`, `idx_projects_user_id`, `idx_projects_manager_id`,
`idx_users_role`, `idx_notifications_status` — 모두 동적 검색 조건에서
등치 비교로 쓰이는 컬럼이다.

**조인·필터에 쓰이는 FK**

`idx_project_history_project_id`, `idx_budget_project_id`, `idx_files_project_id`,
`idx_activity_logs_user_id`, `idx_notifications_user_id` —
과제 상세 화면 하나를 열 때 이력·연구비·첨부파일을 각각 `project_id`로 조회한다.
PostgreSQL은 FK를 걸어도 참조하는 쪽에 인덱스를 자동 생성하지 않으므로 직접 만들어야 한다.

**늘리지 않은 것들**

`title`에는 인덱스를 걸지 않았다.
검색이 `ILIKE '%keyword%'`라 B-tree가 쓰이지 않기 때문이다(→ `운영-성능판단.md` 4절).

그 외 컬럼도 조회 조건에 등장하지 않으면 만들지 않았다.
인덱스는 조회를 돕는 대신 INSERT·UPDATE·DELETE마다 함께 갱신되어야 하고
디스크도 차지한다. 쓰이지 않는 인덱스는 이득 없이 쓰기 비용만 늘린다.

## 요약

| 항목 | 결정 |
|---|---|
| 소유 관계 FK | `ON DELETE CASCADE` — 부모가 사라지면 함께 정리 |
| 행위자 참조 FK | `ON DELETE SET NULL` — 사람은 지워도 기록은 보존 |
| `NULL` 행위자 해석 | 주인 없는 자료로 보고 ADMIN에게만 권한 부여 |
| 상태 전이 | `VALID_TRANSITIONS` 맵으로 코드에서 강제 |
| 전이 우회 | MANAGER 이상 허용, 단 이력·로그·알림은 그대로 기록 |
| 인덱스 | 정렬 1 + 검색 조건 5 + FK 5, 총 11개 |
