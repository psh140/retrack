# 설계 판단 — 인증과 인가

> 대상 코드: `JwtInterceptor`, `JwtUtil`, `@RequiredRole`, `spring-mvc.xml`, `frontend/src/components/RoleRoute.jsx`

인증(누구인가)과 인가(무엇을 할 수 있는가)를 어디서 어떻게 검사할지 정한 기록이다.

---

## 1. Spring Security를 쓰지 않은 이유

Spring Security를 도입하지 않고 `HandlerInterceptor` 하나로 처리했다.

판단의 근거는 두 가지다.

**인증 수단이 JWT 하나뿐이다.** 폼 로그인, 세션, OAuth, Remember-Me 같은 여러 수단을
동시에 지원할 필요가 없다. Security의 필터 체인이 제공하는 가치의 상당 부분은
여러 인증 방식을 조합하고 그 순서를 관리하는 데 있는데, 여기서는 조합할 대상이 없다.

**권한 구조가 단순하다.** 역할이 네 개이고 상하 관계가 일직선이다.
표현식 기반 접근 제어나 메서드 보안 어노테이션이 필요할 만큼 규칙이 복잡하지 않다.

반대로 도입 시 치러야 하는 비용은 분명하다.
Spring Boot가 아니라 XML 설정 기반이므로 `SecurityFilterChain` 등록,
`DelegatingFilterProxy` 연결, 인증 실패 핸들러 커스터마이징을 모두 직접 써야 한다.
얻는 것 대비 설정 코드가 더 늘어난다고 판단했다.

인터셉터는 `spring-mvc.xml`에서 경로 단위로 등록한다.

```xml
<mvc:interceptors>
    <mvc:interceptor>
        <mvc:mapping path="/api/**"/>
        <mvc:exclude-mapping path="/api/auth/**"/>
        <ref bean="jwtInterceptor"/>
    </mvc:interceptor>
</mvc:interceptors>
```

로그인·회원가입은 토큰이 없는 상태로 들어오므로 `/api/auth/**`만 제외하고
나머지 API 전체에 적용한다. 새 컨트롤러를 추가해도 별도 등록 없이 검사 대상이 된다.

## 2. `@RequiredRole` — 선언적 인가

메서드에 필요한 최소 권한을 어노테이션으로 붙인다.

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiredRole {
    String value();
}
```

인터셉터는 `HandlerMethod`에서 이 어노테이션을 꺼내 검사한다.

```java
HandlerMethod handlerMethod = (HandlerMethod) handler;
RequiredRole requiredRole = handlerMethod.getMethodAnnotation(RequiredRole.class);

if (requiredRole != null && !hasPermission(role, requiredRole.value())) {
    sendError(response, HttpServletResponse.SC_FORBIDDEN, "접근 권한이 없습니다.");
    return false;
}
```

권한 규칙이 컨트롤러 메서드 바로 위에 붙어 있어, 그 API의 접근 조건을 알려고
설정 파일을 따로 열어볼 필요가 없다. 경로 패턴으로 관리하면 URL이 바뀔 때마다
설정도 함께 고쳐야 하는데, 어노테이션은 메서드를 따라다닌다.

**어노테이션이 없는 API는 로그인만 되어 있으면 통과한다.**
인가는 선택이고 인증은 필수라는 뜻이다. 목록 조회처럼 로그인한 사용자면
누구나 볼 수 있는 API가 다수라 이 기본값을 택했다.

대신 권한이 필요한 API에 어노테이션을 빠뜨리면 조용히 열린다.
이 기본값의 대가이므로, 새 API를 추가할 때 어노테이션 여부를 확인해야 한다.

## 3. 권한 계층 — 배열 인덱스 비교

역할을 낮은 순으로 나열한 리스트를 두고 `indexOf()` 위치를 비교한다.

```java
private static final List<String> ROLE_HIERARCHY = Arrays.asList(
        "VIEWER", "RESEARCHER", "MANAGER", "ADMIN"
);

private boolean hasPermission(String userRole, String requiredRole) {
    int userLevel = ROLE_HIERARCHY.indexOf(userRole);
    int requiredLevel = ROLE_HIERARCHY.indexOf(requiredRole);
    if (userLevel == -1 || requiredLevel == -1) {
        return false;
    }
    return userLevel >= requiredLevel;
}
```

`@RequiredRole("RESEARCHER")`를 붙이면 RESEARCHER·MANAGER·ADMIN이 통과한다.
상위 권한이 하위 권한을 자동으로 포함하므로 역할별로 허용 목록을 나열할 필요가 없다.

`indexOf()`가 `-1`을 반환하는 경우, 즉 목록에 없는 역할 문자열은 거부한다.
비교식만 두면 `-1 >= -1`이 참이 되어 알 수 없는 역할이 통과하므로 앞에서 끊는다.

이 구조의 한계는 **일직선 계층만 표현할 수 있다는 것**이다.
"예산은 볼 수 있지만 과제는 수정할 수 없는 역할"처럼 상하 관계로 정렬되지 않는 권한은
배열 위치로 나타낼 수 없다. 그런 요구가 생기면 역할×기능 매트릭스로 옮겨가야 한다.

## 4. 프론트엔드 검사와 백엔드 검사의 역할 구분

프론트엔드에도 같은 이름의 권한 검사가 있다.

```jsx
const ROLE_ORDER = ['VIEWER', 'RESEARCHER', 'MANAGER', 'ADMIN'];

if (ROLE_ORDER.indexOf(userRole) < ROLE_ORDER.indexOf(role)) {
  return <Navigate to="/dashboard" replace />;
}
```

**이 검사는 보안 장치가 아니다.**

`RoleRoute`의 판정은 전적으로 브라우저 안에서 이뤄지고, 판정에 쓰이는 값도
사용자 쪽에 있다. 사용자가 그 값을 바꾸면 화면은 그대로 열린다.
개발자 도구를 열 수 있는 사람에게 프론트엔드 검사는 통과 가능한 관문이다.

그럼에도 두는 이유는 **UX** 때문이다.
권한 없는 메뉴를 눌렀을 때 화면이 뜬 뒤 API가 403을 뱉어 빈 표가 남는 것보다,
아예 진입을 막고 대시보드로 돌려보내는 편이 낫다.
접근할 수 없는 기능을 화면에서 감추는 것도 같은 목적이다.

**실제 방어선은 백엔드 하나뿐이다.**
프론트엔드 검사를 뚫어 화면을 열더라도, 그 화면이 호출하는 API는 모두
`JwtInterceptor`를 지난다. 데이터는 서버가 내주지 않으면 나오지 않는다.

그래서 두 곳의 검사는 같은 규칙을 쓰지만 성격이 다르다.
프론트엔드는 화면 정리, 백엔드는 접근 통제다.
프론트엔드 검사가 빠져도 데이터는 새지 않지만, 백엔드 검사가 빠지면 그대로 뚫린다.

## 5. `JWT_SECRET` fail-fast

서명 키는 환경변수에서 읽고, 없거나 짧으면 **기동 자체를 실패시킨다.**

```java
public JwtUtil() {
    String secret = System.getenv("JWT_SECRET");
    if (secret == null || secret.length() < 32) {
        throw new IllegalStateException("환경변수 JWT_SECRET이 설정되지 않았거나 32자 미만입니다.");
    }
    this.key = Keys.hmacShaKeyFor(secret.getBytes());
}
```

기본값을 두지 않은 것이 핵심이다.
`getenv`가 `null`일 때 하드코딩된 문자열로 대체하는 코드를 넣으면,
환경변수를 빠뜨린 서버가 아무 경고 없이 뜨고 그 서버가 발급한 토큰은
소스에 적힌 키로 누구나 위조할 수 있다. 배포 실수가 침해로 이어진다.

`JwtUtil`은 `@Component`라 컨텍스트 초기화 시점에 생성된다.
생성자에서 예외가 나면 애플리케이션 기동이 중단되므로,
잘못 설정된 서버는 요청을 한 건도 받지 못한다.

길이 32자 하한은 HMAC-SHA256의 키 길이 요구(256비트)에서 온다.
`Keys.hmacShaKeyFor()`가 짧은 키에 대해 예외를 던지므로 그 전에 명시적으로 끊는다.

## 6. 토큰 변조 방어

서명 검증을 통과했다고 페이로드가 안전한 값이라는 보장은 없다.

`isValid()`는 서명과 만료만 확인한다.

```java
public boolean isValid(String token) {
    try {
        getClaims(token);
        return true;
    } catch (JwtException | IllegalArgumentException e) {
        return false;
    }
}
```

`subject`에는 `userId`가 문자열로 들어 있고, 꺼낼 때 `Long.parseLong()`을 거친다.

```java
public Long getUserId(String token) {
    return Long.parseLong(getClaims(token).getSubject());
}
```

여기서 `NumberFormatException`이 발생할 수 있다.
서명 키를 알아내 직접 서명한 토큰이나, 다른 방식으로 만들어진 토큰에서
`subject`가 숫자가 아니면 파싱 단계에서 터진다.

이 예외를 인터셉터에서 잡아 401로 바꾼다.

```java
Long userId;
try {
    userId = jwtUtil.getUserId(token);
} catch (NumberFormatException e) {
    sendError(response, HttpServletResponse.SC_UNAUTHORIZED, "유효하지 않은 토큰입니다.");
    return false;
}
```

잡지 않으면 인터셉터에서 던져진 런타임 예외가 그대로 올라가 500이 된다.
인증 실패를 서버 오류로 응답하는 셈이라 상태 코드의 의미가 어긋나고,
스택트레이스가 응답에 실릴 여지도 생긴다. 401로 정정해 내보낸다.
