## 1. AWS 콘솔 작업

콘솔 UI 조작이라 명령어가 없다. 선택값과 근거는
[`배포-체크리스트.md`](배포-체크리스트.md) 2번 섹션에 정리했다.

핵심만 다시 적으면:

- **스토리지는 기본 8GB → 20GB로 반드시 늘린다.** postgres:14 + tomcat:9-jdk11 + node 빌드
  이미지 + nginx를 받으면 이미지만 2~3GB고, 빌드 캐시와 로그가 쌓이면 8GB로는 부족하다.
  프리티어 무료 한도가 30GB라 20GB까지는 추가 비용이 사실상 없다.
- **보안 그룹에서 HTTP(80)를 빠뜨리기 쉽다.** 인스턴스 시작 마법사의 방화벽 항목은
  SSH만 기본 체크되어 있고 HTTP·HTTPS는 꺼져 있다. 80이 막히면 Certbot HTTP-01 챌린지가
  실패해 **인증서 발급 자체가 불가능**하다.
- **고급 세부 정보**: 종료 방지 활성화. 크레딧 사양의 '무제한'은 해제(표준) —
  t3는 기본이 무제한이라 CPU 크레딧 소진 시 자동 과금된다.
- **Elastic IP는 할당 후 반드시 인스턴스에 연결한다.** 연결하지 않으면 IP만 점유한 채 요금이 나간다.
  다만 2024년 2월부터는 **연결 여부와 무관하게** 퍼블릭 IPv4에 시간당 요금이 부과되므로,
  연결한다고 무료가 되는 것은 아니다. 연결이 필요한 이유는 과금 회피가 아니라
  중지·재시작 시 IP가 바뀌지 않게 해 DNS A 레코드를 유지하기 위해서다.
- **Route 53에서 도메인을 사면 호스팅 영역이 자동 생성**되어 네임서버 위임 작업이 필요 없다.
  A 레코드만 추가하면 된다(루트 + `www` 각각 1개, TTL 300).

DNS 전파 확인:

```powershell
# Windows (로컬)
Resolve-DnsName hughpark.com -Type A -Server 8.8.8.8
```

```bash
# macOS / Linux (로컬)
dig +short hughpark.com @8.8.8.8
```

`52.78.210.188`이 나오면 전파 완료다. Route 53은 보통 60초 이내에 반영된다.

## 2. SSH 접속 준비

### 2-1. 키 파일 권한 조정 (필수)

**권한이 느슨하면 SSH가 접속을 거부한다** (`UNPROTECTED PRIVATE KEY FILE`).
OS별로 방법이 다르다.

```powershell
# Windows — 상속 제거 후 본인에게 읽기 권한만 부여
icacls "<키 경로>\retrack-key.pem" /inheritance:r /grant:r "$($env:USERNAME):R"
```

```bash
# macOS / Linux
chmod 400 ~/.ssh/retrack-key.pem
```

### 2-2. 접속

```bash
ssh -i "<키 경로>/retrack-key.pem" ubuntu@52.78.210.188
```

- 첫 접속 시 `Are you sure you want to continue connecting (yes/no/[fingerprint])?`가 뜬다.
  **`yes`를 전부 입력**해야 한다. `y`는 인식되지 않는다.
- 프롬프트가 `ubuntu@ip-172-31-36-244:~$`로 바뀌면 성공이다.
  여기 보이는 `172.31.x.x`는 VPC 내부용 프라이빗 IP로, 외부 접속과는 무관하다.
- 계정명이 `ubuntu`인 것은 Ubuntu 공식 AMI의 기본 관리자 계정이기 때문이다
  (Amazon Linux는 `ec2-user`).

### 2-3. 매번 긴 명령을 치기 싫다면 (선택)

`~/.ssh/config` (Windows는 `C:\Users\<사용자>\.ssh\config`)에 등록하면 `ssh retrack`으로 접속된다.

```
Host retrack
    HostName 52.78.210.188
    User ubuntu
    IdentityFile ~/.ssh/retrack-key.pem
```

## 3. 서버 초기 세팅

### 3-1. 시스템 업데이트 + Swap 2GB

```bash
sudo apt update && sudo apt upgrade -y

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

free -h
```

**Swap을 만드는 이유**: t3.small의 RAM은 2GB뿐인데, 프론트엔드 컨테이너를 빌드할 때
Vite가 메모리를 대량으로 쓴다. Swap 없이는 빌드 도중 OOM으로 죽는다.
`/etc/fstab`에 등록해야 재부팅 후에도 유지된다.

**실행 중 보라색 전체화면(needrestart)이 뜬다.** 재시작할 서비스를 묻는 창이며 엔터로 넘어간다.

결과 확인 — `Swap` 행이 `2.0Gi`면 정상:

```
               total        used        free      shared  buff/cache   available
Mem:           1.9Gi       469Mi       219Mi       2.7Mi       1.4Gi       1.4Gi
Swap:          2.0Gi          0B       2.0Gi
```

### 3-2. 커널 업그레이드 반영을 위한 재부팅

`apt upgrade` 이후 아래 경고가 출력됐다.

```
Pending kernel upgrade!
Running kernel version:
  6.17.0-1017-aws
Diagnostics:
  The currently running kernel version is not the expected kernel version 7.0.0-1009-aws.
```

새 커널이 설치됐지만 구 커널로 동작 중이라는 뜻이다. **컨테이너를 올리기 전인 이 시점에
재부팅하는 것이 좋다.** 서비스 기동 후에 하면 다운타임이 생긴다.

```bash
sudo reboot
```

SSH 연결이 끊긴다(정상). 30초~1분 후 같은 명령으로 재접속한다.
Elastic IP를 연결해 뒀으므로 주소는 바뀌지 않는다.

재접속 후 확인:

```bash
uname -r        # 7.0.0-1009-aws 로 바뀌었는지
free -h         # Swap 2.0Gi가 유지되는지 (fstab 등록 덕분에 유지된다)
```

## 4. Docker 설치

우분투 기본 저장소의 `docker.io` 대신 **Docker 공식 저장소**를 등록해 설치했다.
`docker-compose.prod.yml`에서 쓴 `!reset` / `!override` 문법이 Compose v2.24.0 이상을 요구하는데,
배포판 기본 패키지는 이보다 낮을 수 있기 때문이다.

```bash
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

sudo usermod -aG docker $USER
```

**`usermod`는 재접속해야 적용된다.** `exit` 후 다시 SSH로 붙어야 `sudo` 없이 docker를 쓸 수 있다.

검증:

```bash
docker --version         # Docker version 29.7.1
docker compose version   # v5.3.1 — v2.24.0 이상 요구조건 충족
docker run hello-world   # sudo 없이 실행되는지 확인
```

## 5. 코드 배치 및 컨테이너 기동

### 5-1. 저장소 clone

```bash
sudo apt install -y git      # Ubuntu 24.04에는 이미 설치되어 있었다
cd ~
git clone https://github.com/psh140/retrack.git
cd retrack
```

**HTTPS 주소로 clone해야 한다.** 로컬 저장소의 remote는 SSH(`git@github.com:...`)인데
서버에는 GitHub SSH 키가 없다. 공개 저장소이므로 HTTPS는 로그인 없이 받아진다.

### 5-2. `.env` 작성

`DB_PASSWORD`와 `JWT_SECRET`은 **서버에서 새로 생성**한다(로컬 값 재사용 금지).

```bash
cd ~/retrack
cp .env.example .env

sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=$(openssl rand -hex 16)|" .env
sed -i "s|^JWT_SECRET=.*|JWT_SECRET=$(openssl rand -hex 32)|" .env

chmod 600 .env
nano .env        # MAIL_USERNAME / MAIL_PASSWORD 2개만 직접 입력
```

**`MAIL_PASSWORD`는 구글 계정 비밀번호가 아니라 Gmail 앱 비밀번호다.**
Gmail은 외부 앱의 계정 비밀번호 SMTP 로그인을 차단하므로, 2단계 인증 계정에서 발급하는
16자리 앱 비밀번호를 써야 한다(`myaccount.google.com` → 보안 → 2단계 인증 → 앱 비밀번호).
`.env`에는 4자씩 공백으로 끊긴 형태를 큰따옴표로 감싸 넣는다 — 따옴표는 Compose가 벗겨낸다.

```
MAIL_PASSWORD="xxxx xxxx xxxx xxxx"
```

값을 화면에 노출하지 않고 검증하는 방법:

```bash
grep -E 'your-|at-least-32' .env                              # 출력 없으면 예시값이 안 남은 것
awk -F= '/^[A-Z]/ {print $1" = "length($2)" chars"}' .env      # 값 대신 길이만
```

정상 길이는 `DB_PASSWORD` 32자, `JWT_SECRET` 64자(hex라 바이트의 2배),
`MAIL_PASSWORD` 21자(16자 + 공백 3 + 따옴표 2)다.

### 5-3. WAR 업로드

`backend/target/`은 `.gitignore` 대상이라 clone에 포함되지 않는다. 디렉터리부터 만든다.

```bash
mkdir -p ~/retrack/backend/target      # 서버
```

```powershell
# 로컬(Windows)에서 전송
scp -i "<키 경로>\retrack-key.pem" `
    "<프로젝트 경로>\backend\target\retrack-backend-1.0-SNAPSHOT.war" `
    ubuntu@52.78.210.188:/home/ubuntu/retrack/backend/target/
```

**디렉터리를 먼저 만들지 않으면** Docker가 마운트 경로를 빈 디렉터리로 생성해버려
Tomcat이 WAR를 배포하지 못한다.

WAR에 최신 소스가 반영됐는지는 압축을 열어 확인할 수 있다(시크릿 분리 이후 재빌드했는지 등):

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = [System.IO.Compression.ZipFile]::OpenRead("<WAR 경로>")
$zip.Entries | Where-Object { $_.FullName -like "*spring-db.xml" }
```

### 5-5. 외부 접속 확인

```powershell
Invoke-WebRequest http://hughpark.com -UseBasicParsing          # 200, Server: nginx
Invoke-WebRequest http://hughpark.com/api/projects -UseBasicParsing   # 401
```

`/api`가 **401이면 정상이다.** 502가 아니라 401이라는 것은 nginx 프록시가 백엔드에 도달했고,
Tomcat이 WAR를 배포했으며, JWT 필터가 동작 중이라는 뜻이다.

### 5-6. 운영 DB에는 계정이 없다 — ADMIN 승격 필요

`docker-compose.prod.yml`이 `seed.sql` 마운트를 제외하므로 운영 DB에는 테이블만 있고
**사용자 계정이 하나도 없다.** 로컬 테스트 계정으로는 로그인할 수 없다.

1. 브라우저에서 회원가입 — 이때 권한은 DB 컬럼 기본값에 따라 `VIEWER`로 생성된다
2. DB에서 직접 ADMIN으로 승격한다

```bash
docker exec -it retrack-db psql -U retrack -d retrack \
  -c "UPDATE users SET role='ADMIN' WHERE username='<가입한 아이디>';"
```

ADMIN이 없으면 사용자 관리·통계·활동 로그 페이지에 접근할 수 없다.

## 6. HTTPS 인증서 발급

### 6-1. 설정 파일을 개발용/운영용으로 분리한 이유

443 서버 블록은 **인증서 파일이 실재해야 nginx가 기동한다.** 로컬 개발 환경에는 인증서가 없으므로,
기존 `nginx.conf` 하나에 443을 추가하면 로컬에서 프론트엔드 컨테이너가 뜨지 않는다.

| 환경 | 사용 설정 | 적용 방식 |
|---|---|---|
| 로컬 개발 | `frontend/nginx.conf` (80만) | Dockerfile이 이미지에 COPY |
| 운영(EC2) | `frontend/nginx.prod.conf` (80 리다이렉트 + 443) | `prod.yml`에서 볼륨 마운트로 덮어쓰기 |

볼륨 마운트라서 **설정만 바꿀 때는 이미지 재빌드 없이 컨테이너 재생성으로 반영**된다.
`docker-compose.prod.yml`의 frontend에 추가한 항목:

```yaml
ports: !override
  - "80:80"
  - "443:443"
volumes:
  - ./frontend/nginx.prod.conf:/etc/nginx/conf.d/default.conf:ro
  - /etc/letsencrypt:/etc/letsencrypt:ro
  - /var/www/certbot:/var/www/certbot:ro
```

`nginx.prod.conf`에는 기존 SPA 폴백과 `/api` 프록시(업스트림 DNS 재조회 방식)를 그대로 옮기고,
HTTPS 종단이 Nginx이므로 `proxy_set_header X-Forwarded-Proto $scheme;`를 추가했다.

### 6-2. 인증서 발급 (standalone)

standalone 방식은 certbot이 80 포트를 직접 점유하므로 frontend를 잠시 멈춰야 한다.

```bash
sudo snap install --classic certbot
sudo ln -s /snap/bin/certbot /usr/bin/certbot

cd ~/retrack
docker compose -f docker-compose.yml -f docker-compose.prod.yml stop frontend

sudo certbot certonly --standalone \
  -d hughpark.com -d www.hughpark.com \
  --agree-tos -m <알림 받을 이메일> --no-eff-email

docker compose -f docker-compose.yml -f docker-compose.prod.yml start frontend
```

발급 경로: `/etc/letsencrypt/live/hughpark.com/{fullchain.pem, privkey.pem}` (유효기간 90일)

### 6-4. 자동 갱신 훅 — 반드시 설정해야 한다

certbot은 설치 시 자동 갱신 타이머를 등록하지만, **갱신도 standalone으로 동작하므로
frontend 컨테이너가 80 포트를 잡고 있으면 실패한다.** 그대로 두면 90일 뒤 인증서가 만료된다.

갱신 전후로 컨테이너를 자동 제어하도록 훅 스크립트를 배치한다.

`/etc/letsencrypt/renewal-hooks/pre/stop-frontend.sh`

```sh
#!/bin/sh
cd /home/ubuntu/retrack || exit 0
docker compose -f docker-compose.yml -f docker-compose.prod.yml stop frontend
```

`/etc/letsencrypt/renewal-hooks/post/start-frontend.sh`

```sh
#!/bin/sh
cd /home/ubuntu/retrack || exit 0
docker compose -f docker-compose.yml -f docker-compose.prod.yml start frontend
```

```bash
sudo chmod +x /etc/letsencrypt/renewal-hooks/pre/stop-frontend.sh \
              /etc/letsencrypt/renewal-hooks/post/start-frontend.sh
```

`post` 훅을 쓴 이유: `deploy` 훅은 갱신에 성공했을 때만 실행되지만,
`post`는 성공·실패와 무관하게 실행되므로 어떤 경우에도 서비스가 되살아난다.

**Windows에서 스크립트를 만들어 올릴 때 줄바꿈이 CRLF면 `bad interpreter` 오류로 실행되지 않는다.**
`file <경로>` 결과가 `POSIX shell script`로 나오는지 확인한다.

```

Hook 'post-hook' ran ... Container retrack-frontend Started
```

- `ran with error output`은 오류가 아니다. docker compose가 진행 상황을 stderr로 출력할 뿐이다.

## 8. 트러블슈팅

### 8-1. HTTPS 전환 직후 로그인·회원가입이 403으로 막힘

**증상** — HTTP로 서비스할 때는 정상이던 로그인이, HTTPS 적용 후 갑자기 실패했다.
백엔드 로그에는 로그인 시도 흔적(`AuthMapper.findByEmail`)조차 남지 않았다.

**진단** — Nginx 액세스 로그에서 요청 주체별로 응답이 갈렸다.

| 요청 | 응답 |
|---|---|
| 브라우저 `POST /api/auth/login` | **403** (20바이트) |
| `Origin` 헤더 없는 CLI 요청 | **401** (정상적인 인증 실패) |

브라우저만 실패한다는 것은 `Origin` 헤더가 원인이라는 뜻이다. 실제로 CLI 요청에
`Origin: https://hughpark.com`을 붙이자 동일하게 403이 재현됐다.

**원인** — `spring-mvc.xml`의 CORS 허용 출처가 개발용 하나뿐이었다.

```xml
<mvc:mapping path="/api/**" allowed-origins="http://localhost:3000" ... />
```

그런데 **HTTP로 서비스할 때는 이 설정으로도 문제가 없었다.** Spring은 `Origin` 헤더와
요청 URL의 scheme/host/port가 모두 같으면 same-origin으로 보고 CORS 검사를 건너뛰기 때문이다.

HTTPS로 바꾸자 어긋났다.

```
브라우저가 보낸 Origin : https://hughpark.com
백엔드가 인식한 요청   : http://hughpark.com   ← Nginx가 백엔드로 HTTP로 프록시
                        scheme 불일치 → cross-origin 판정 → allowed-origins에 없음 → 403
```

`proxy_set_header X-Forwarded-Proto $scheme;`를 넣어두었지만, **Tomcat은 RemoteIpValve 같은
별도 설정 없이는 이 헤더로 `request.getScheme()`을 바꾸지 않는다.**

**해결** — Nginx가 백엔드로 넘길 때 `Origin` 헤더를 비운다.

```nginx
location /api {
    ...
    proxy_set_header Origin "";
}
```

Nginx 뒤는 항상 동일 출처이므로 이 헤더를 전달할 이유가 없고, 헤더가 없으면 Spring은
CORS 검사를 수행하지 않는다. 브라우저 관점에서도 same-origin 요청이라 preflight(OPTIONS)가
발생하지 않으므로 이 방식으로 충분하다.

설정 반영은 마운트된 파일을 교체한 뒤 리로드하면 된다(컨테이너 재생성 불필요).

```bash
docker exec retrack-frontend nginx -t         # 문법 검사
docker exec retrack-frontend nginx -s reload  # 무중단 반영
```

**백엔드 설정도 함께 수정(적용 완료)** — 즉시 복구는 Nginx로 했지만, 근본 원인인
백엔드 허용 목록도 바로잡아 재배포했다.

```xml
allowed-origins="http://localhost:3000,https://hughpark.com,https://www.hughpark.com"
```

**두 조치를 모두 유지한다.** Nginx 뒤는 항상 동일 출처이므로 Origin 제거가 정당하고,
백엔드 설정은 Nginx를 거치지 않는 접근에 대한 대비다.

`spring-mvc.xml`은 WAR에 포함되므로 재빌드가 필요하다. 백엔드 재배포 절차는 아래와 같다.

```powershell
# 1. 로컬 빌드 (테스트 포함)
mvn -B -f backend\pom.xml clean package

# 2. WAR에 변경이 실제로 들어갔는지 확인 (선택)
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = [System.IO.Compression.ZipFile]::OpenRead("<WAR 경로>")
# → spring-mvc.xml 엔트리를 읽어 내용 확인

# 3. 전송
scp -i <키> backend\target\retrack-backend-1.0-SNAPSHOT.war ubuntu@52.78.210.188:/home/ubuntu/retrack/backend/target/
```

```bash
# 4. 컨테이너 재생성 — Tomcat이 WAR를 다시 배포한다
cd ~/retrack
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate backend
docker logs retrack-backend --tail 12    # "Deployment ... has finished" 확인
```

**빌드 환경 주의** — 로컬에 JDK 11이 없어 JDK 21로 빌드했다. `pom.xml`의 `source/target 11`
설정이 클래스 파일 버전을 55로 맞추므로 `tomcat:9-jdk11` 컨테이너에서 정상 동작한다.
빌드 실패에 대비해 **기존 WAR를 먼저 백업**하는 편이 안전하다. `clean`이 지워버리기 때문이다.

### 8-2. `docker compose up -d`가 컨테이너를 재생성하지 않는 경우

마운트된 설정 파일만 바꾸면 compose 정의 자체는 변하지 않으므로 컨테이너가
`Running` 상태로 유지되고 새 설정이 적용되지 않는다. 이때는 리로드하거나
`docker compose restart frontend`로 다시 읽게 한다.

### 8-3. PowerShell에서 SSH로 SQL을 보낼 때 따옴표가 사라지는 문제

PowerShell이 네이티브 실행 파일에 인자를 넘기며 큰따옴표를 제거해, psql이 SQL을
단어별 인자로 받아 무시한다.

```
psql: warning: extra command-line argument "username," ignored
```

큰따옴표는 `\"`로, SQL 내부의 작은따옴표는 `''`로 이스케이프한다.

```powershell
ssh -i <키> ubuntu@<IP> 'docker exec retrack-db psql -U retrack -d retrack -c \"UPDATE users SET role=''ADMIN'' WHERE user_id=1\"'
```

## 9. 구성 판단 정리

작업 순서와 별개로, 배포 구성에서 왜 그렇게 했는지를 모아둔다.

### 9-1. Compose 오버라이드 전략

로컬과 운영이 같은 `docker-compose.yml`을 공유하고, 운영에서만 `docker-compose.prod.yml`을
덧붙인다. 뒤에 지정한 파일이 앞의 설정을 덮어쓴다.

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

로컬 개발은 `docker-compose.yml` 단독으로 계속 쓰므로 운영 설정의 영향을 받지 않는다.

문제는 **병합 규칙**이다. 스칼라 값은 뒤 파일이 덮어쓰지만,
`ports`나 `volumes` 같은 **리스트는 기본적으로 병합된다.**
운영에서 항목을 빼려 해도 앞 파일의 항목이 그대로 남는다.

Compose는 이 상황을 위해 두 개의 태그를 제공한다.

| 태그 | 동작 | 이 프로젝트에서의 용도 |
|---|---|---|
| `!reset` | 상위 파일의 값을 지운다 | db·backend의 호스트 포트 노출 제거 |
| `!override` | 리스트를 병합하지 않고 통째로 교체한다 | seed.sql 마운트 제외, frontend 포트 교체 |

```yaml
db:
  ports: !reset []          # 5432 노출 제거
  volumes: !override        # 목록 전체 교체 — seed.sql이 빠지고 demo.sql이 들어간다
    - postgres-data:/var/lib/postgresql/data
    - ./sql/schema.sql:/docker-entrypoint-initdb.d/01_schema.sql
    - ./sql/demo.sql:/docker-entrypoint-initdb.d/02_demo.sql
```

**두 태그 모두 Compose v2.24.0 이상에서만 동작한다.**
배포판 기본 패키지(`docker.io`)는 이보다 낮을 수 있어 Docker 공식 저장소로 설치했다(→ 4장).
서버에서 `docker compose version`으로 먼저 확인할 것.

### 9-2. 운영에서 호스트 포트를 닫은 이유

로컬에서는 DB(5432)와 백엔드(8080)를 호스트에 열어 둔다.
DBeaver로 붙거나 Postman으로 백엔드를 직접 때려보기 위해서다.

운영에서는 둘 다 닫았다.

```yaml
db:
  ports: !reset []
backend:
  ports: !reset []
```

컨테이너끼리는 도커 네트워크 안에서 `db:5432`, `backend:8080`으로 통신하므로
호스트 포트 노출은 기능상 필요가 없다. 외부 요청은 전부 nginx가 `/api`로 프록시한다.

열어둘 실익이 없는 반면 대가는 분명하다.
호스트 포트를 열면 보안 그룹 설정과 무관하게 공격면이 늘어난다.
특히 도커는 iptables를 직접 조작하므로 호스트 방화벽 규칙이 의도대로 적용되지 않을 수 있다.

기동 후 `ps`로 확인한다(→ 5-4). `retrack-db`가 `5432/tcp`로만 보이고
`0.0.0.0:5432->5432/tcp`가 아니면 정상이다.

### 9-3. `initdb.d`는 첫 기동에만 실행된다

`/docker-entrypoint-initdb.d/`에 마운트한 SQL은 postgres 이미지가 자동 실행해 준다.
단, **데이터 볼륨이 비어 있을 때만** 실행된다.

이미 데이터가 있는 볼륨에서는 이 디렉터리를 아예 쳐다보지 않는다.
운영 중인 DB에 `demo.sql`을 새로 넣거나 갱신해도 컨테이너를 재시작하는 것만으로는
아무 일도 일어나지 않는다. 마운트를 고쳤는데 반영이 안 된다면 대부분 이 이유다.

그래서 별도로 `scripts/reset-demo.sh`를 두었다.
컨테이너에 이미 마운트된 경로의 파일을 `psql`로 직접 재실행하는 방식이다.

```bash
docker exec -i retrack-db \
    psql -U retrack -d retrack -v ON_ERROR_STOP=1 \
    -f /docker-entrypoint-initdb.d/02_demo.sql
```

`demo.sql`이 맨 앞에서 `TRUNCATE`로 전체를 비우므로 몇 번을 돌려도 같은 상태가 된다.
DB의 `files` 레코드가 사라지면 디스크의 업로드 파일은 고아가 되므로
스크립트가 `uploads/`도 함께 정리한다.

방문자가 데모 데이터를 바꿔놓아도 매일 원상 복구되도록 cron에 걸어 쓴다.

### 9-4. 프론트엔드 이미지 — 멀티 스테이지 빌드

`frontend/Dockerfile`은 두 단계로 나뉜다.

```dockerfile
# Stage 1: React 빌드
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Nginx로 정적 파일 서빙
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

최종 이미지에는 `nginx:alpine`과 빌드 결과물(`dist`)만 남는다.
Node 런타임과 `node_modules`는 빌더 스테이지에 머물고 최종 이미지로 넘어오지 않는다.

이미지 크기가 줄어드는 것이 일차 효과지만, 운영 관점에서는
**실행 환경에 빌드 도구가 남지 않는다는 점**이 더 중요하다.
서빙만 하는 컨테이너에 패키지 매니저와 소스가 함께 들어 있을 이유가 없다.

`package*.json`을 먼저 복사하고 `npm ci`를 실행한 뒤 소스를 복사하는 순서도 의도적이다.
소스만 바뀌었을 때 의존성 설치 레이어가 캐시에 적중해 재빌드가 빨라진다.

다만 빌드가 EC2에서 이뤄지므로 메모리를 쓴다.
t3.small(2GB)에서도 Vite 빌드가 실패해 swap 2GB를 추가해야 했다(→ 3-1).
