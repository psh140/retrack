# AWS 비용 방어 설정 (Retrack)

> 트래픽 급증 및 공격 상황에서 예기치 못한 AWS 요금 청구를 방지하기 위한 운영 설정 기록
>
> 최종 갱신: 2026-08-06

---

## 1. 배경

Retrack은 단일 EC2 인스턴스에 Docker Compose로 배포된 개인 프로젝트다.
개인 계정으로 운영하는 만큼, 공격이나 비정상 트래픽으로 인한 요금 폭탄이 실질적인 리스크였다.

다만 대응에 앞서 **"어떤 요금 항목이 실제로 트래픽에 비례하는가"** 를 먼저 정리했다.
막연한 불안 대신 실제 과금 구조를 파악해야 방어 지점이 명확해지기 때문이다.

### 요금 항목별 트래픽 민감도

| 항목 | 트래픽 급증 시 | 비고 |
|---|---|---|
| EC2 인스턴스 시간 | 변동 없음 | Auto Scaling 미사용, 시간당 고정 |
| EBS 스토리지 | 변동 없음 | 볼륨 크기 기준 |
| Elastic IP | 변동 없음 | 시간당 고정 |
| **아웃바운드 데이터 전송** | **비례 증가** | **주요 리스크** |
| Route 53 쿼리 | 비례 증가 | DNS flood 시. 현 규모에선 영향 미미 |

**결론: 단일 인스턴스 구성에서 비용 리스크는 사실상 아웃바운드 데이터 전송(egress) 하나로 수렴한다.**

아웃바운드는 월 100GB까지 무료이며, 초과분부터 GB 단위로 과금된다.
서울 리전(ap-northeast-2) 단가는 미국 리전보다 높으므로, 정확한 수치는 EC2 온디맨드 요금 페이지에서 확인할 것.

### 현실적인 위험 수준

소형 인스턴스는 네트워크 대역폭 자체가 병목이므로, 수 TB 규모의 egress가 발생하려면 회선을 장시간 포화시켜야 한다.
실제로는 **요금 폭탄보다 서비스 다운이 먼저 발생**할 가능성이 높다.

실측으로도 뒷받침된다. 배포 이후 시간당 아웃바운드는 수십 KB 수준으로,
월 환산 시 100MB 안팎 — 무료 한도 100GB의 0.1% 수준이다.
현 트래픽 규모에서 과금 구간에 도달하려면 평상시의 1,000배 이상이 한 달 내내 지속되어야 한다.

따라서 목표는 "완벽한 공격 차단"이 아니라 **"인지하지 못한 채 요금이 누적되는 상황의 방지"** 로 설정했다.

## 2. 적용한 대책

### 2.1 AWS Budgets 예산 알림 (기존)

월 예산을 설정하고 실제 사용액 도달 시 이메일 알림.
사후 인지 수단이며, 이것만으로는 진행 중인 과금을 멈출 수 없다.

### 2.2 CloudWatch 경보 + EC2 자동 중지 (신규)

예산 알림의 한계를 보완하는 **차단기(kill switch)** 역할.
임계값 초과 시 알림과 동시에 인스턴스를 중지시켜 과금 자체를 끊는다.

**설정값**

| 항목 | 값 |
|---|---|
| 경보 이름 | `awsec2-{instance-id}-GreaterThanThreshold-NetworkOut` |
| 네임스페이스 | AWS/EC2 |
| 지표 | NetworkOut |
| 통계 | **합계 (Sum)** |
| 기간 | 1시간 |
| 조건 | `> 2147483648` (2GB) |
| 연속 기간 | 1 |
| 누락 데이터 처리 | 누락으로 처리 |
| 작업 1 | SNS 주제로 이메일 알림 |
| 작업 2 | **EC2 인스턴스 중지** |

**설계 근거**

- **통계는 반드시 `합계`**: `평균`으로 설정하면 "1시간 동안 총 몇 바이트가 나갔는가"를 측정할 수 없어 지표로서 의미가 없다.
- **임계값 2GB**: 배포 완료(2026-08-03) 이후 운영 구간의 실측 트래픽은 시간당 40KB~110KB 수준이다.
  2GB는 평상시의 약 2만 배다.
  다만 배포 당일 **18MB의 일회성 스파이크**가 관측됐으므로, 오탐 여지를 따질 때는 평상시가 아니라
  이 관측 최대치를 기준으로 봐야 한다 — 그래도 **약 120배 여유**가 있어 오탐 가능성은 낮다.
  기준선은 배포 이후 구간만 사용했다. 배포 이전(~08-02)은 시간당 5KB 수준이지만
  서비스가 동작하지 않던 시기라 평상시로 볼 수 없다.
- **중지(stop) 선택**: 종료(terminate)는 인스턴스를 영구 삭제하므로 절대 선택하면 안 된다. 중지는 EBS 볼륨이 보존되어 재시작 가능하다.

**설정 검증 (2026-08-06)**

생성 직후 경보 상태가 `데이터 부족`으로 표시되어 지표 연결을 의심했으나,
`기록(History)` 탭에서 **생성 24초 후 `데이터 부족` → `정상` 전환**이 확인되어 정상 동작으로 판정했다.

- 경보 상세 화면의 상태 타임라인이 생성 이전 구간을 회색(`데이터 부족`)으로 칠하는 것은
  그 기간에 경보가 존재하지 않아 상태 정보가 없기 때문이며 오류가 아니다.
- 설정 직후의 `데이터 부족`은 첫 평가 주기가 끝나지 않은 정상 상태다.
  다만 **몇 시간이 지나도 유지된다면** 차원(InstanceId) 불일치를 의심해야 한다.
  이 경우 경보는 존재하지 않는 대상을 감시하므로 영원히 발동하지 않는다.

> **미검증 항목**: 경보가 실제로 인스턴스를 중지시키는지는 발동 테스트를 하지 않았다.
> 작업 설정에 EC2 중지가 등록된 것은 확인했으나 end-to-end 동작은 확인되지 않은 상태다.
> 테스트하려면 `aws cloudwatch set-alarm-state`로 상태를 강제 전환해야 하고, 실제로 서비스가 중단된다.

### 2.3 일별 NetworkOut 경보 (누수 감시)

2.2의 시간당 경보는 **급격한 폭주만** 포착한다.
시간당 1.9GB처럼 임계값 바로 아래를 유지하면 경보는 한 번도 울리지 않지만 월 egress는 1.3TB에 달한다.
이 구간을 메우기 위해 일 단위 경보를 별도로 두었다.

**설정값**

| 항목 | 값 |
|---|---|
| 경보 이름 | `hughpark-daily-networkout-3gb` |
| 지표 | NetworkOut (2.2와 동일 인스턴스) |
| 통계 | 합계 (Sum) |
| 기간 | **1일** |
| 조건 | `> 3221225472` (3GB) |
| 작업 | SNS 알림만 — **EC2 중지 없음** |

**설계 근거**

- **임계값 3GB**: 무료 한도 100GB/월은 하루 평균 3.3GB에 해당한다.
  3GB에서 알림이 오면 무료 한도를 넘기기 직전에 인지할 수 있다.
  평상시는 하루 약 1.6MB(시간당 66KB 기준)이므로 약 1,900배 여유가 있어 오탐 여지가 없다.
- **중지 액션을 걸지 않은 이유**: 시간당 2GB는 명백한 이상 상황이지만,
  하루 3GB는 정상적인 트래픽 증가일 수 있다. 포트폴리오 사이트가 어딘가에 공유되어
  방문자가 몰리는 상황에서 자동 중지가 걸리면 **가장 노출이 필요한 시점에 서비스가 멈춘다.**
  이 구간의 판단은 사람이 한다.
- **알림 트리거는 `경보 상태`만 선택**: `정상`(복구 알림)은 중복이고,
  `데이터 부족`은 인스턴스를 정상적으로 중지해도 발동하여 오알림의 원인이 된다.

> 기간이 1일이라 첫 평가가 완결될 때까지 `데이터 부족` 상태가 유지된다(최대 24시간).
> 그 이상 지속되면 차원(InstanceId) 설정을 의심할 것.

**두 경보의 역할 분담**

| | 2.2 시간당 경보 | 2.3 일별 경보 |
|---|---|---|
| 잡는 것 | 급발진 (공격·폭주) | 완만한 누수 |
| 임계값 | 시간당 2GB | 하루 3GB |
| 동작 | 알림 + **EC2 중지** | 알림만 |

### 2.4 SNS 이메일 구독

CloudWatch 경보 생성 화면에서 SNS 주제를 만들면 **주제만 생성되고 이메일 구독은 자동으로 연결되지 않는 경우가 있다.**
이 상태에서는 인스턴스는 중지되지만 알림 메일이 오지 않아, 서비스 다운을 며칠간 인지하지 못할 수 있다.

SNS 콘솔 → 주제 → 구독 탭에서 **상태가 `확인됨(Confirmed)`인지 반드시 검증할 것.**
`확인 대기 중`이면 수신 메일의 `Confirm subscription` 링크를 클릭해야 활성화된다.

### 2.5 Elastic IP 확인

자동 중지 설정의 **전제 조건**.

Elastic IP가 연결되어 있지 않으면 인스턴스를 중지 후 재시작할 때 퍼블릭 IP가 변경되고,
DNS A 레코드가 존재하지 않는 주소를 가리키게 되어 도메인이 끊긴다.

차단기는 정상 동작했는데 복구 후 사이트가 열리지 않는 상황을 막기 위해 반드시 선행 확인이 필요하다.

> 현재 상태: Elastic IP 할당 및 인스턴스 연결 완료

## 3. 경보 발동 시 대응 절차

인스턴스가 자동 중지되고 알림 메일을 수신한 경우:

1. **즉시 재시작하지 않는다.** 공격이 진행 중이면 재시작 직후 동일 상황이 반복된다.
   세 컨테이너 모두 `restart: unless-stopped`라 인스턴스를 시작하는 즉시 서비스가 자동으로 올라온다.
2. **원인 파악.** 인스턴스를 재시작한 뒤 nginx 액세스 로그를 확인한다.
   ```bash
   docker compose logs frontend | tail -200
   ```
   서비스명은 `frontend`다(컨테이너명은 `retrack-frontend`). `nginx`라는 서비스는 없다.

   인스턴스가 중지 상태여도 EBS는 보존되므로 컨테이너 로그는 남는다.
   다만 `docker-compose.prod.yml`에서 서비스당 `max-size 10m × max-file 3`(최대 30MB) 로테이션을
   걸어 두었으므로 **폭주 상황에서는 초기 구간이 순환 삭제된다.**
   중지 직전 30MB만 남는다고 보고, 공격 시작 시점까지 거슬러 올라갈 수 있다고 가정하지 않는다.
3. **원인별 조치**
   - 특정 IP의 집중 요청 → 보안 그룹에서 해당 대역 차단
   - 특정 엔드포인트 반복 호출 → nginx rate limit 적용 후 재시작
   - 정상적인 트래픽 증가 → 임계값 상향 조정
4. **경보 상태 확인.** CloudWatch 경보 액션은 **상태가 전환되는 시점에만** 실행된다.
   `경보` 상태가 유지되는 동안에는 중지가 다시 걸리지 않으므로, 재시작 직후 곧바로 또 멈출 걱정은 없다.
   트래픽이 정상으로 돌아오면 다음 평가 주기(1시간)에 자동으로 `정상`으로 전환된다.

   즉시 되돌려야 한다면 CLI를 쓴다. 콘솔에는 상태를 수동 전환하는 메뉴가 없다.
   ```bash
   aws cloudwatch set-alarm-state --alarm-name <경보 이름> \
     --state-value OK --state-reason "manual reset after recovery"
   ```

> 참고: 인스턴스 중지 중에도 Elastic IP와 EBS 볼륨 요금은 계속 발생한다. "중지 = 0원"이 아니다.

## 4. 미완료 항목 (예정)

다음 프로젝트를 서브도메인으로 추가하는 시점에 nginx 설정 변경과 함께 일괄 진행 예정.

### 4.1 nginx rate limit

애플리케이션 레벨 1차 방어. 인프라 변경 없이 서버 내에서 완결된다.

```nginx
# http 블록
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

# server 블록
location /api/ {
    limit_req zone=api burst=20 nodelay;
    limit_conn conn 10;
}
```

로그인 및 회원가입 엔드포인트는 더 낮은 rate로 별도 적용 예정.

### 4.2 Cloudflare 프록시 도입

- 원본 EC2 IP 은닉 → 직접 공격 표면 제거
- 정적 리소스 엣지 캐싱 → egress 절감 및 응답 속도 개선
- 무료 플랜 기본 DDoS 방어

**도입 후 필수 후속 작업**

- 보안 그룹 80/443 인바운드를 Cloudflare IP 대역으로 제한
  (미적용 시 원본 IP를 아는 공격자가 프록시를 우회)
- SSL/TLS 모드를 **Full (strict)** 로 설정
  (Flexible 설정 시 리다이렉트 루프 또는 구간 암호화 누락 발생)
- nginx `real_ip` 설정
  (미적용 시 모든 액세스 로그의 클라이언트 IP가 Cloudflare IP로 기록되어,
  활동 로그 AOP를 포함한 애플리케이션 로직에 영향)

```nginx
set_real_ip_from <Cloudflare IP 대역>;
real_ip_header CF-Connecting-IP;
```

### 4.3 Cloudflare Origin Certificate 전환

현재 Let's Encrypt 사용 중이나, 서브도메인 추가 시마다 인증서 발급 및 갱신 관리가 누적된다.

Origin Certificate는 와일드카드(`*.hughpark.com`)를 지원하고 유효기간이 길어,
서브도메인을 몇 개 추가하든 인증서 작업이 발생하지 않는다.
Cloudflare 프록시 뒤에서만 유효하므로 4.2와 함께 적용해야 한다.

### 4.4 서브도메인 확장 구조

Cloudflare 도입을 완료하면 신규 프로젝트 추가 시 필요한 작업은 다음 두 가지로 축소된다.

1. Cloudflare DNS에 A 레코드 1건 추가 (프록시 활성화)
2. nginx `server_name` 기반 server 블록 추가

인증서, 보안 그룹, 경보, Elastic IP는 도메인/인스턴스 단위 설정이므로 재작업이 필요 없다.

급격한 폭주는 시간당 경보가 즉시 끊고, 임계값 아래의 완만한 누수는 일별 경보가
무료 한도를 넘기기 전에 알린다.

남은 항목은 방어 심도를 높이고 운영 편의를 개선하기 위한 것으로, 긴급도는 낮다.

## 부록: 설정 중 발생한 이슈

기록 목적으로 남긴다. 동일 작업 재수행 시 참고.

**EC2 인스턴스 화면의 간편 경보 생성 다이얼로그 이슈**

`EC2 → 인스턴스 → 상태 및 경보 → 작업 → CloudWatch 경보 관리` 경로의 간편 창에서,
`샘플링할 데이터 유형`을 변경해도 임계값 입력 필드의 검증 규칙이 이전 지표(CPU 사용률, 0~100) 기준으로 남아 있어
바이트 단위 값 입력이 거부되는 현상이 있었다.

→ 지표를 **가장 먼저** 선택한 뒤 나머지 항목을 채우거나,
정식 CloudWatch 콘솔(`CloudWatch → 경보 → 경보 생성`)을 사용하면 회피 가능하다.

**콘솔 한글 표기 차이**

- `NetworkOut` → 한글 콘솔에서는 **"네트워크 출력"** 으로 표시된다 ("네트워크 아웃" 아님)
- `Sum` → **"합계"**
- `Per-Instance Metrics` → **"인스턴스별 지표"**

**리전 확인**

CloudWatch, SNS 모두 리전별로 독립적이다.
리전이 서울(ap-northeast-2)이 아니면 인스턴스 지표나 SNS 주제가 목록에 나타나지 않는다.
