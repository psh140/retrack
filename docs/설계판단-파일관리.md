# 설계 판단 — 파일 관리

> 대상 코드: `FileService`, `LocalFileStorageStrategy`, `FileServiceTest`, `sql/schema.sql`

첨부파일은 DB 레코드와 실제 파일이라는 두 개의 저장소에 나뉘어 존재한다.
둘 중 하나만 성공한 상태가 남지 않도록 순서와 실패 처리를 정한 기록이다.

---

## 1. `@Transactional`과 파일시스템의 경계

Spring의 `@Transactional`이 되돌리는 것은 DB 커넥션의 트랜잭션이다.
`file.transferTo()`로 디스크에 쓴 결과는 트랜잭션 관리 대상이 아니므로 롤백해도 그대로 남는다.

즉 "DB는 롤백됐는데 파일은 남아 있는" 상태가 자동으로 정리되지 않는다.
그래서 파일이 얽힌 작업은 **어느 쪽을 먼저 하고, 뒤쪽이 실패하면 앞을 어떻게 되돌릴지**를
코드에서 직접 정해야 한다.

---

## 2. 업로드 — 보상 처리

파일 저장을 먼저 하고 DB INSERT를 나중에 한다.
INSERT가 실패하면 이미 저장된 파일을 `catch` 블록에서 직접 지운다.

```java
String savedName = UUID.randomUUID().toString() + "." + extension;
String savedPath = fileStorageStrategy.store(file, savedName);

// ... FileVO 구성 ...

try {
    fileMapper.insert(fileVO);
} catch (Exception e) {
    // DB INSERT 실패 시 저장된 파일 롤백
    fileStorageStrategy.delete(savedPath);
    throw e;
}
```

순서를 뒤집어 DB INSERT를 먼저 하면 `file_path`에 넣을 값이 아직 없다.
저장 경로는 `store()`의 반환값이므로 파일 저장이 선행되어야 한다.

예외는 삼키지 않고 다시 던진다. 보상 처리는 파일시스템 정리까지만 담당하고,
사용자에게 실패를 알리는 것은 `GlobalExceptionHandler`의 몫이다.

---

## 3. 삭제 — DB 먼저, 파일 나중

`deleteFile()`은 DB DELETE를 먼저 하고 파일시스템을 지운다.

```java
fileMapper.delete(projectId, fileId);
fileStorageStrategy.delete(file.getFilePath());
```

순서를 뒤집으면 파일을 지운 뒤 DB DELETE가 실패했을 때 **실체 없는 레코드**가 남는다.
목록에는 보이는데 다운로드하면 실패하는 상태이므로 사용자에게 그대로 드러난다.

현재 순서에서 뒤쪽이 실패하면 반대로 **주인 없는 파일**이 디스크에 남는다.
이쪽은 디스크 용량 문제이지 사용자에게 잘못된 화면을 보여주지는 않는다.
어느 쪽도 완전하지 않은 상황에서 사용자에게 노출되지 않는 쪽을 택했다.

한편 삭제 권한 판정에는 스키마 정책이 얽혀 있다.
`FILES.uploaded_by`는 `ON DELETE SET NULL`이라 업로더가 탈퇴하면 `null`이 된다.
이 경우를 "주인이 없는 파일"로 보고 ADMIN에게만 삭제를 허용한다.

```java
if (!"ADMIN".equals(requesterRole) &&
        (file.getUploadedBy() == null || !file.getUploadedBy().equals(requesterUserId))) {
    throw new UnauthorizedException("본인이 업로드한 파일만 삭제할 수 있습니다.");
}
```

## 4. 과제 삭제 — CASCADE가 닿지 않는 곳

`FILES.project_id`는 `ON DELETE CASCADE`다.

```sql
project_id  BIGINT NOT NULL REFERENCES PROJECTS(project_id) ON DELETE CASCADE,
```

과제를 지우면 DB의 `files` 레코드는 함께 사라진다.
그러나 CASCADE의 범위는 DB 안까지이고 디스크의 실제 파일은 그대로 남는다.
게다가 레코드가 사라지면 파일 경로를 알 방법도 없어져 나중에 정리할 수도 없다.

그래서 `deleteProject()`는 **레코드가 살아 있는 동안** 파일 경로를 모아 먼저 지운다.

```java
public void deleteProject(Long projectId, Long userId) throws IOException {
    getProject(projectId);
    fileService.deleteAllFilesByProject(projectId);   // 파일시스템 정리
    projectMapper.deleteProject(projectId);           // CASCADE로 files 레코드 삭제
}
```

`deleteAllFilesByProject()`는 `findAllByProjectId()`로 경로 목록을 조회한 뒤
파일시스템에서만 지운다. DB 레코드 삭제는 CASCADE에 맡긴다.

## 5. 업로드 검증

세 가지를 통과해야 저장에 도달한다.

**확장자 화이트리스트**

```java
private static final List<String> ALLOWED_EXTENSIONS = Arrays.asList(
        "pdf", "hwp", "hwpx", "doc", "docx", "xls", "xlsx", "ppt", "pptx",
        "jpg", "jpeg", "png", "zip"
);
```

블랙리스트가 아니라 화이트리스트를 쓴다.
막을 확장자를 나열하는 방식은 목록에 없는 새로운 형식이 통과하지만,
허용할 것을 나열하면 모르는 형식은 기본적으로 막힌다.
실제로 업무에서 오가는 문서 형식은 열세 종으로 한정되므로 나열이 가능하다.

**저장명과 원본명의 분리**

저장 파일명은 `UUID.randomUUID()`로 새로 만들고, 원본 파일명은 DB `file_name` 컬럼에만 남긴다.
사용자가 넣은 문자열이 디스크 경로에 그대로 쓰이지 않으므로
파일명 충돌과 파일명을 통한 조작이 함께 차단된다.
다운로드 시에는 DB에 보관한 원본명을 헤더에 실어 원래 이름으로 내려준다.

**경로 구분자 제거**

```java
// 원본 파일명에서 경로 구분자 제거 후 확장자 추출
String originalName = new File(rawName).getName();
```

`getOriginalFilename()`은 브라우저가 보낸 값이라 신뢰할 수 없다.
`../../etc/passwd` 같은 값이 들어오더라도 `new File(rawName).getName()`이
마지막 경로 요소만 남기므로 상위 디렉터리 참조가 제거된다(path traversal 방어).

이 값은 확장자 추출과 DB 저장에 쓰인다.
값이 `null`이거나 비어 있으면 그 시점에 `BadRequestException`으로 끊는다.

## 6. 저장소 교체 가능 구조

`FileService`는 `FileStorageStrategy` 인터페이스에만 의존한다.

```java
public interface FileStorageStrategy {
    String store(MultipartFile file, String savedName) throws IOException;
    Resource load(String filePath) throws IOException;
    void delete(String filePath) throws IOException;
}
```

현재 구현체는 Docker 볼륨에 쓰는 `LocalFileStorageStrategy`이고,
주입은 `spring-mvc.xml`의 빈 선언으로 이뤄진다.

```xml
<bean id="fileStorageStrategy" class="com.retrack.storage.LocalFileStorageStrategy">
    <constructor-arg value="/app/uploads/"/>
</bean>
```

S3로 옮긴다면 `S3FileStorageStrategy`를 새로 구현하고 이 빈 선언만 교체하면 된다.
`FileService`의 업로드·삭제 순서와 보상 로직은 저장소가 무엇이든 그대로 유지된다.

## 7. 관련 테스트

`FileServiceTest` 5건이 위 판단들을 검증한다.

| 테스트 | 검증 대상 |
|---|---|
| `uploadFile_DB실패시파일롤백` | DB INSERT 실패를 주입해 저장된 파일의 `delete()` 호출을 확인 (2번) |
| `uploadFile_불허확장자_BadRequestException` | `.exe` 차단, 저장 자체가 호출되지 않음을 확인 (5번) |
| `uploadFile_파일명없음_BadRequestException` | 파일명 `null` 차단, 저장 미호출 확인 (5번) |
| `deleteFile_RESEARCHER_타인파일_UnauthorizedException` | 소유권 검증 (3번) |
| `deleteFile_ADMIN_타인파일_성공` | ADMIN 분기 시 DB·파일시스템 삭제 모두 호출 확인 (3번) |

롤백 테스트는 `FileStorageStrategy`를 목으로 두고 `fileMapper.insert()`가
예외를 던지도록 만든 뒤, `delete("/uploads/xxx.pdf")`가 한 번 호출됐는지를 확인한다.
저장소 구현이 바뀌어도 이 검증은 그대로 유효하다.
