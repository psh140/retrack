### 1-1. 시크릿 분리 — 완료 (2026-07-27)

저장소가 **공개 상태**임을 확인했다(GitHub API 200). 커밋된 평문 자격증명은 이미 외부에 노출된 것으로

**주의 — `spring-db.xml` 하드코딩 문제**

`docker-compose.yml`이 `DB_HOST`·`DB_PORT`·`DB_NAME`·`DB_USER`·`DB_PASSWORD`를 넘기고 있었지만,
백엔드는 이 값들을 **전혀 읽지 않고** `spring-db.xml`에 직접 적힌 접속 정보를 쓰고 있었다.
compose만 `${DB_PASSWORD}`로 바꿨다면 DB 접속이 그대로 옛 비밀번호를 향해 실패했을 것이다.
`spring-mvc.xml:96`의 기존 패턴(`#{systemEnvironment['...']}`)에 맞춰 교체했다.

`JWT_SECRET`은 `JwtUtil.java:34`에서 `System.getenv()`로 정상적으로 읽고 있어 별도 수정이 없었다.

**변경 후 필수 절차**

1. WAR 재빌드 — `spring-db.xml`은 WAR에 포함되므로 재빌드해야 반영된다
2. 실제 PostgreSQL 계정 비밀번호 변경 — `POSTGRES_PASSWORD`는 볼륨 최초 생성 시에만 적용되므로,
   기존 볼륨에서는 `ALTER USER`로 직접 바꿔야 한다
   ```bash
   docker exec -it retrack-db psql -U retrack -d retrack \
     -c "ALTER USER retrack WITH PASSWORD '<새 비밀번호>';"
   ```
3. JWT 서명키 교체로 기존 발급 토큰은 모두 무효 — 재로그인 필요

**git 히스토리**: 재작성하지 않기로 결정했다. 노출된 값을 폐기한 이상 히스토리에 남은 옛 값은
무의미하고, GitHub 캐시·기존 클론본은 어차피 회수가 불가능하다.

**EC2 배포 시**: 로컬 `.env` 값을 재사용하지 말고 서버에서 새로 생성한다.

### 1-2. 운영용 compose 오버라이드 — 완료 (2026-07-29)

`docker-compose.prod.yml`을 작성했다. 로컬 개발 환경(`docker-compose.yml`)은 그대로 두고
EC2에서만 오버라이드를 적용한다.

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

| 대상 | 개발 | 운영 | 상태 |
|---|---|---|---|
| seed.sql 마운트 | 테스트 데이터 자동 주입 | 제거 | [x] |
| DB `5432:5432` | 호스트에 노출 | 노출 제거 — 백엔드가 같은 도커 네트워크로 접근 | [x] |
| 백엔드 `8080:8080` | 호스트에 노출 | 노출 제거 — Nginx가 `/api`를 프록시 | [x] |
| 프론트엔드 포트 | `3000:80` | `80:80` — 표준 HTTP 포트 | [x] |
| 재시작 정책 | 없음 | `restart: unless-stopped` (3개 서비스) | [x] |

**주의 — Compose 버전**

포트 노출 제거와 seed.sql 제외에 `!reset` / `!override` 태그를 썼다.
이 태그는 **Docker Compose v2.24.0 이상**에서만 동작하므로, EC2 세팅 후 버전을 확인해야 한다.

```bash
docker compose version
```

**검증 결과** (로컬, 2026-07-29)

```bash
# 운영 오버라이드 적용 시 — db·backend 포트 노출 없음, seed.sql 없음, frontend 80:80
docker compose -f docker-compose.yml -f docker-compose.prod.yml config

# 개발 단독 실행 시 — 기존과 동일 (5432 / 8080 / 3000 노출, seed.sql 유지)
docker compose -f docker-compose.yml config
```

### 참고 — 백엔드 재배포 시 Nginx 502 (해결 완료, 2026-07-29)

과거에는 백엔드 컨테이너를 재생성할 때마다 `/api` 요청이 전부 502가 되어
`docker compose restart frontend`가 필요했다. Nginx가 기동 시점에 조회한 IP를
계속 재사용하는데 컨테이너 IP는 재생성 시 바뀌기 때문이다.

`frontend/nginx.conf`에 Docker 내장 DNS resolver를 명시하고 프록시 대상을 변수로 지정해
매 요청마다 재조회하도록 수정했다. **이제 백엔드 재배포 후 frontend 재시작이 불필요하다.**

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;

location /api {
    set $backend_host backend;
    proxy_pass http://$backend_host:8080$request_uri;
    ...
}
```

→ 상세: [`troubleshooting-nginx-업스트림-DNS캐싱.md`](troubleshooting-nginx-업스트림-DNS캐싱.md)
